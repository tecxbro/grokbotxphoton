# WT-03 integration requests

WT-03 implements its lane against committed F0 without editing shared contracts or wiring. These are proposed WT-00/WT-01 integration steps, not completed integration.

1. Register `createTextMessageModule` from `src/features/text-messages/module.ts` and add an approved package export. The example under `examples/wt-03/register.ts` is compile-only. The factory requires a trusted `binding(context)` with the exact project/account/line/space scope, native chat ID and serving phone (including the actual `shared` sentinel when applicable). Logical line IDs are not assumed to be phone numbers.
2. Supply `requestId(action, services)` from the current shared executor attempt. F0 `ExecutionServices` does not contain the current outbox ID. Do not guess that request ID equals the idempotency key, or scan a bounded page of outbox rows. Consider adding an explicit shared current-request field in a later F0 revision; until then use the factory callback.
3. The shared executor must persist the outbox/task and its current claim before calling a handler. WT-03 uses F0 `children` directly, with IDs `wt03-` plus SHA-256 of `[requestId,index]`, and canonical-content stable keys. It guards writes against the current outbox claim/task generation/cancellation. The executor owns outbox results/revisions/attempts, scheduling and context authorization. Wire recovery to invoke the handler for safe blocked preparation failures; completed children are skipped. Never requeue dispatching/unknown children without externally verified reconciliation. The conservative recovery codec authorizes completion only when the scoped parent already records executor completion.
4. Supply registered compilers through the lazy `compilers()` callback using the shared registry. WT-03 does not import WT-04/05/06/07 implementation files. Each delegated leaf must produce one public SDK content builder. Media staging and native/card/poll eligibility remain the owning compiler's responsibility. Run cross-lane tests after committed integration.
5. F0's `ContentCompiler` returns a single `ContentInput`; it cannot represent ordered variadic sends with per-child outcomes. `content.compose` is an executor-only operation, deliberately not a registered opaque multi-send compiler. Do not invoke one SDK variadic send behind a journal entry. If a future caller needs compile-only compose output, introduce a typed sequence plan through WT-00 rather than a fake content builder.
6. Resource adapters must map stored scoped references to actual SDK messages, including native grouped part metadata. Mutation requires the stored owner and correct direction. Reaction removal needs the actual reaction message with `content.target` and emoji; the lane retains up to 1000 returned handles per resource resolver. After eviction/restart, resolve the actual handle using authoritative SDK/provider state or fail unavailable; never synthesize a message from a guessed ID. Persisting a primitive checkpoint does not itself restore an SDK object.
7. Current host adapters must honor closed registered-stream records: WT-03 closes a stream record atomically before `open` and consumes it once. `open` must retrieve the already-authorized producer without independently rejecting WT-03's consumption claim. A crash before/during collection leaves it unavailable. Factory buffering is explicit; native progressive delivery is not implemented. If progressive delivery is required later, approve a way to observe the initial message handle and every edit outcome before enabling it.
8. Account/conversation availability is unknown. Validate deployed provider/device eligibility during authorized installation. The pinned provider marks the entire chat read; do not present `message.markRead` as target-only. No live test has been authorized or performed.
