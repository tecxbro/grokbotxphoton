# Card and interaction lifecycle
## Public execution
module.ts:createFeatureModule registers the three handlers with the frozen public FeatureModule contract; operations.ts:executeCardOperation orchestrates configured resources, scoped domain transactions and shared executeChild. sdk.ts:mapCardOperation maps public app/customizedMiniApp/edit builders and verifies trusted native chat and line. Existing compatibility APIs remain separate and are not registered by the new entry point.

## Session ownership and restart
session-codec.ts:encodeCardSession emits bounded versioned data only, and restoreCardSession requires a genuine original public SDK Message. Public getMessage may retain provider session metadata while the provider remains alive; it does not establish cold-process rehydration. Never attach serialized metadata to a reconstructed Message. Missing original handles return requires_original_session. Durable public domain records persist resource, task, principal, generation, card/template and session/expiry/action bindings. F0 provides no session-payload slot, so full snapshot persistence requires a shared contract extension; no private checkpoints or overloaded text columns are used.

## Update ordering and transaction scope
update-ordering.ts:assertCurrentCardRevision uses admission-time expected revision plus authoritative card/session/reference records and active claim. Card revision is a domain state machine: even revisions are settled, odd revisions reserve an in-flight update. Reserve and finalize each consume one CAS revision; successful updates advance by two. A durable odd revision blocks later updates after cancellation, failure or restart until shared reconciliation. Queue updates per original card in a module; CAS excludes separate module/process dispatches. Prepare resources/builders outside transactions, then recheck authority immediately before every provider effect. Preserve original message/line/chat. Undefined edit results mean executor completion, never a missing ID or new bubble. Refresh metadata via the public original space.getMessage where available without replacing original message identity.

## Callback trust and atomic continuation
interaction-adapter.ts:authenticateInteraction delegates raw bytes to the actual injected backend contract. normalizeInteraction bounds and validates the internal assertion; it defines no public wire protocol and never consumes app.messages taps. reducer.ts:applyCardInteraction binds full scope, card/session/message, participant, allowed action, task, generation, expiry and nonce. Sessions are single-use: nonce equals the issued internal session identity; backend authentication provides trust, not nonce secrecy. Session revision is consumed atomically with createContinuation referencing the backend event ID. The host must durably capture the authenticated event including selection before invoking reduction; F0 exposes no feature-owned inbox writes. Wake is the shared runtime's post-commit responsibility. Unknown sessions return unresolved for host capture and never resolve against a recent task. Missing backend configuration only blocks callback ingress.

## Configuration prerequisites
Trusted host templates provide exact HTTPS origins, extension identity when customized, verified installed-extension evidence when live, and real update URL mapping for universal cards. Request identities must be stable and scoped to principal/task/generation. Expected update revisions are immutable admission values. The existing single transport supplies native space/phone mapping and public SDK objects; no clients or listeners are created here.

## Host wiring
Construct one CardRuntime(options), pass that instance to createFeatureModule(runtime), and register its handlers with the injected executor. The same runtime.snapshot(sessionId) supplies an inert binding to applyCardInteraction after authenticateInteraction and durable host capture. Snapshot access is internal trusted host code; it is not a public endpoint. The adapter returns unresolved when a restarted host has no retained binding. There is no implemented generic cold-session recovery.

The public revision protocol applies only to cards created by this new entry point. Legacy card records use the older codec/revision protocol and require explicit integration migration; new handlers never silently adopt them. Template extension/origin/live/callback identity is fingerprinted at send and checked before update.
